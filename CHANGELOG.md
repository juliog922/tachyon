# Changelog

All notable changes to this project are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- The tokenizer reads mmBERT's Metaspace pre-tokenizer (a cut before every space, `▁` prepended to each piece), and finds non-special added tokens such as Granite's `<body>` in the text before merging, as Hugging Face does: mmBERT's and Granite Embedding 311M's tokenizers match `tokenizers` on all 10,000 fixture strings.

- `tachyon run` takes a catalog name (`gemma-4-e4b`) as well as a model directory.
- Model weights take VRAM from the GPU's memory pool (`Context::alloc_pooled`), which keeps freed VRAM for the process until `Context::trim` gives it back: a model returning from the host tier reuses the VRAM the last one left instead of fresh VRAM, which the driver clears first (the L40S copies into fresh VRAM at 70% of the rate). `Engine::unload`, and `Engine::expire` when a keep-alive runs out, give VRAM back to the system; a model moved out to make room does not. GPUs without memory pools allocate as before. The `switch` bench reports the cost of giving VRAM back.

- Attention kernels take a `group` argument and launch a block per four query heads (`ptx::HEADS_PER_BLOCK`, was `HEADS_PER_KV`); `KV_256`/`KV_512` take `group` too. The `decode` bench passes the window it had been missing since step 7.
- `Engine::open` is gone: an engine is made with `Engine::new` and loads models by name.
- The `generate` bench checks the step-6 gate (≥ 80% of the roofline) on the RTX 3060 only; on other GPUs it prints the figure.
- Q4 conversion picks each group's scale among 13 candidates by least rounding error, instead of the largest weight over 7: top-1 agreement with bfloat16 Gemma 4 E4B rises from 83% to 88% at the same size and speed (`scripts/agreement.py` measures it). Quantization runs on every core.
- `Detokenizer` keeps its unfinished bytes in place instead of reallocating them per token.
- Attention gives each block at least 24 positions and loads a chunk of positions' keys and values at once, instead of relying on prefetch hints, which the RTX 3060 ignores: 11 µs → 8 µs per sliding layer at short contexts.

### Added

- Step 11d: speech. `Message::audio` plays clips after a message's text; the chat template gives each `<|audio>`, a `<|audio|>` slot per soft token (`audio::count`) and `<audio|>`, token for token as Hugging Face's processor does. `Engine::chat` runs the model's audio tower (opened with its first clip, freed with the model's VRAM, counted in the limit) and fills the slots in prefill as images'. `tachyon run <model> --audio=FILE <prompt>` and `tachyon transcribe <model> <file>`. Tests: the template against the reference's tokens, E4B's picks against Hugging Face's bfloat16 transcriptions of both clips, a transcription through the engine. `audio` benchmark: the tower and whole transcriptions, as time and real-time factor (gate ≤ 0.05). `scripts/agreement.py` takes `speech.ref`. `Message` is no longer `Eq`: audio holds floats.
- Step 11c-2: `audio`, Gemma 4's audio tower on the GPU. `convert` (from `model::convert`, when the checkpoint has a tower) writes `audio.wpk`: the subsampling convolutions, `f16` matrices with their clip bounds (queries, keys and values fused, the GLU's halves interleaved), the norms (the feed-forward blocks' residual weight folded into their post-norms), each layer's query scale and its relative positions' keys, computed once. `Tower::soft_tokens` resamples to 16 kHz, takes the log-mel features and runs the tower in `f16` with an `f32` residual stream; `audio::soft_tokens` counts them as the processor does. Kernels: `SUBSAMPLE` (convolution, layer norm, ReLU), `ATTEND_AUDIO` (chunked local attention with relative positions and soft-capped logits), `LCONV` (the light convolution's depthwise taps, norm and `SiLU`); `GEMM_CLIP` gains a `SiLU` (mode 3) and a GLU (mode 5); `RMS_F16` can write its norm as `f32`, in place. Tested against the CPU kernel by kernel and, with the weights, against Hugging Face's float32 soft tokens.
- Step 11c-1: audio input. `media::decode_wav` reads WAV (8-bit unsigned to 32-bit PCM, 32- and 64-bit float, plain or `WAVE_FORMAT_EXTENSIBLE`, channels averaged) to the samples `soundfile` gives; `Audio::resampled` (a Kaiser-windowed sinc, polyphase); `media::mel`, Gemma 4's log-mel features (20 ms frames every 10 ms, 512-point FFT, 128 HTK mel bins, up to 30 s), within 1e-4 of `transformers`' extractor. `scripts/media.py audio` writes the WAV and mel fixtures; `scripts/media.py speech` is the audio tower's precision study and references; `scripts/agreement.py` measures Q4's agreement on `vision.ref`'s answers about images.
- Step 11b-2: images in chat. `Message::images` shows images before a message's text (`Message::new` makes one of text only); the chat template gives each `<|image>`, a `<|image|>` slot per soft token at the budget (`Chat::with_budget`, `Load::budget`, 280 by default; `Image::soft_tokens`), and `<image|>`, token for token as Hugging Face's processor does. `Engine::chat` runs the model's vision tower (opened with its first image, freed with the model's VRAM, counted in the limit) and `Decoder::prefill_with` puts the soft tokens in place of their slots' embeddings, across chunk boundaries, the slots reading as the pad token for the per-layer inputs. `tachyon run <model> --image=FILE <prompt>`. Tests: the template against the reference's tokens, E4B's picks against Hugging Face's bfloat16 answers about 3 images at 70 and 280 soft tokens, and an answer through the engine. `vision` benchmark: the tower at every budget, and the time to first token with and without an image.
- Step 11b-1: `vision`, Gemma 4's vision tower on the GPU. `convert` (from `model::convert`, when the checkpoint has a tower) writes `vision.wpk`: `f16` matrices, queries, keys and values fused, gate and up interleaved, each with its clip bounds; `f32` norms. `Vision::soft_tokens` fits an image to a budget, cuts its patches and runs the 16 layers in `f16` with an `f32` residual stream, then pools 3 × 3 and projects into the decoder's 2,560 dimensions. Kernels: `GEMM_CLIP` and `GEMM_CLIP_128`, the encoder's product with Gemma 4's clipped linear layers (input bounds on the fragments, each row's output bounds in the store, the gated GELU in its tanh form); `RMS_F16` (the residual step and the norm), `HEADS_F16` (per-head norms and 2-D RoPE), `POOL_F16`, `ADD_ROWS_F16`. Tested against the CPU kernel by kernel and, with the weights, against Hugging Face's float32 soft tokens.
- Step 11a: `media`, images for Gemma 4's vision encoder with no dependencies. `media::decode` reads PNG (every color type and bit depth, through its own zlib inflate) and baseline or extended sequential JPEG (libjpeg-turbo's integer IDCT, fancy upsampling and YCbCr conversion), turned by the JPEG's EXIF orientation; `Image::resize` is PIL's fixed-point bicubic; `Image::fitted` sizes an image for a soft-token budget (70 to 1,120) as Gemma 4's image processor does. All 50 fixture files decode, and resize at three budgets, to exactly PIL's pixels (`tests/media.rs`); interlaced PNG and progressive JPEG are refused. `scripts/media.py images` writes the fixtures; `scripts/media.py vision` is the vision tower's precision study and writes its references. `Error::Media`.
- Step 10c: `Engine::decide` (Laya: each option's probability for typed questions about a text or a conversation) and `Engine::embed` (Granite: unit vectors, Matryoshka cuts); `Engine::load` recognizes an encoder's directory, which stays in VRAM, counted in the limit. `Encoder::decide` and `Encoder::embed` take text. `tachyon decide <model> <request.json>` (the `laya` package's request shape) and `tachyon embed <model> [--dims=N] <text>...`; `tachyon convert` takes Laya and Granite checkpoints; the catalog lists `laya-multilingual` and `granite-embedding-311m`, which `pull` fetches (repositories are listed with their folders). `Json::dumps` writes JSON as Python does, Laya's form of a structured state. `encoder` benchmark: Laya with 1, 5 and 10 questions per call and Granite with 1 and 64 texts, then each product kernel alone and every call kernel by kernel (`Encoder::timeline`) against the `f16` tensor peaks (`MMA_PEAK_F16`, `MMA_PEAK_F16H`); step-10 gate: one Laya question in ≤ 6 ms and ten in one call in ≤ 4 ms each on an RTX 3060 Laptop (5 ms for one was the plan; the spec records why it moved). The encoder runs as CUDA graphs per padded batch shape; attention on tensor cores (flash attention, 64 queries per block); products in blocks of 64 or 128 tokens with a three- or four-stage `cp.async` pipeline and grouped block order; the gated GELU inside the up product (rows interleaved at load); RoPE on `f16`; layer norm in one pass.

- `tachyon::encoder`, step 10b: `convert` turns a Laya or Granite Embedding checkpoint into a model directory (matrices in `f16`, norms in `f32`, the token embeddings in pinned host memory); `Encoder` runs it on the GPU over sequences packed back to back without padding, in batches of up to `Settings::tokens`: `hidden` (every token's last state), `embeddings` (Granite: the first token's, to unit length) and `logits` (Laya's head and scorer at each option's marker). Kernels in `ptx::encoder`: `GEMM_F16`, the `f16` product on tensor cores (`mma.sync` `m16n8k16`, `f32` sums, `ldmatrix`, two `cp.async` stages) storing `f32`, adding into the residual, or storing `f16` with an optional ReLU; `NORM_F16`; `EMBED_F16`, `ADD_ROWS`, `GATHER_ROWS`; `GELU_F16` (exact, through erf); `ROPE_F32`; `ATTEND_F16`, bidirectional attention over packed sequences, global or within a window. Tested against the CPU reference on the tiny Laya and, with the weights, against the float32 references of 500 decisions and 54 embeddings.

- `tachyon::encoder`, step 10a: `Config` reads a ModernBERT's `config.json` in transformers 5's layout or 4's; `encoder::laya` builds Laya's question sequences exactly as the `laya` package (0.4.5) does, token for token on 500 cases in 17 languages (`Builder`, `Question`, `Kind`, `Budget`), reads a checkpoint's head settings and temperatures (`Head`) and turns option logits into probabilities. `tests/encoder.rs` holds a float32 ModernBERT and Laya head on the CPU, the GPU encoder's future reference, matching PyTorch to 1e-4 on a tiny random Laya (`scripts/encoders.py tiny`) and, with the `models` feature, the real checkpoints' references.
- `scripts/encoders.py`: float32 references for Laya multilingual (500 decisions) and Granite Embedding 311M (54 embeddings), and the precision study that chose f16 for the encoders: Q8 changes 2.4% of Laya's answers, f16 none.

- `tachyon pull [model] [--keep]`, `catalog`, `list`, `rm` and `doctor`. `pull` downloads a Hugging Face checkpoint over 8 connections (`TACHYON_CONNECTIONS`) in 32 MiB ranges, hashes it in order with SHA-256 and flushes it to disk as it arrives, each on its own thread, resumes an interrupted download from its `.part` file, follows the Hub's redirects and asks again when a signed CDN link expires, then converts it into `$TACHYON_HOME` and removes the checkpoint unless `--keep`. Without a name it pulls the largest model that fits in 70% of GPU 0. `TACHYON_HUB` names a mirror.
- `tachyon_cli::net`, networking with `std` only: SHA-256 (SHA-NI when the CPU has it), HMAC and HKDF, AES-128-GCM (AES-NI and PCLMULQDQ), X25519, P-256 ECDSA and RSA (PKCS#1 v1.5 and PSS) verification, X.509 chains checked against the system's trust anchors, a TLS 1.3 client (`TLS_AES_128_GCM_SHA256`, X25519), and HTTP/1.1 with keep-alive, chunked bodies, redirects and ranges. Ported in part from caudal.
- `download` benchmark: SHA-256 and AES-GCM rates, a checkpoint range fetched by `curl` and by Tachyon over one and over eight connections, and conversion time per model. Step-9 gate: over one connection, within 5% of `curl`; SHA-256 faster than any download.

- Gemma 4 E2B: attention takes any multiple of four query heads per key-value head (a block per four heads, `group` blocks per key-value head; E2B has eight over one), and the shared layers' MLPs of a model with `use_double_wide_mlp` are twice as wide (`Config::mlp`). `Config` refuses, as `Error::Unsupported`, what the larger models add (mixture of experts, values equal to keys, no per-layer inputs, other key-value heads in global layers, fewer than four query heads per key-value head), instead of converting a model it would run wrong.
- Several models on one GPU: `Engine::new(gpu, Limits)`, then `Engine::load(name, dir, &Load)` and `Engine::chat(name, &Request)`; `unload`, `tier`, `expire`. Models stay in VRAM within `Limits::vram` (70% of the GPU's by default) and their keep-alive (`Load::keep_alive`, five minutes by default, or `Request::keep_alive` per answer; zero moves a model out at once, `Duration::MAX` keeps it); to make room the least recently used model moves out first, never a pinned one (`Load::pin`) or the one answering. A model moved out is parked in the host-RAM tier within `Limits::host` (half the RAM by default), the oldest parked models freed to disk to make room. A model that cannot fit is `Error::OutOfMemory`; an unknown name `Error::NoModel`.
- `Decoder::park` moves a model's weights to pinned host memory and frees its VRAM; `Parked::resume` brings it back with one copy at PCIe speed, its kernels still compiled. A resumed decoder keeps that pinned copy (`Decoder::shadow_bytes`, counted in the host tier and freed first when the tier needs room), so parking it again copies and allocates nothing. `model::footprint` is the VRAM a model directory takes with given settings.
- `switch` benchmark: time to first token after another resident model against after the same; a model's return from the host tier against copies into reused and into fresh VRAM; pinned and device memory taken and given back; whole switches between E4B and E2B through the host tier and from disk; unloading. Step-8 gate: switching adds ≤ 1 ms, and on native Linux a model returns at ≥ 90% of a copy into reused VRAM (L40S: 96%; under WSL2 the return is printed, not checked).
- Prefill: `Decoder::prefill` feeds prompt tokens a chunk at a time (`Settings::chunk`, 512 by default) through the tensor-core GEMM and the prefill kernels, only the layers that write a key-value cache (24 of E4B's 42); `Engine::chat` prefills all prompt tokens but the last. Sliding caches hold a chunk past the window. The `generate` bench reports time to first token from 64 to 8192 tokens.
- Prefill attention: `kv_256`/`kv_512` store a chunk's keys and values (normalized, rotated) in the cache, then `attend_256p`/`attend_512p` attend each token over its window, a token per grid row, with Q8P out. Attention takes the window apart from the cache size, so a sliding ring can be longer than the window.
- Prefill versions of the small kernels: `ptx::NORM_Q8P` (the residual step over many tokens, Q8P out), `ptx::GEGLU_Q8P` (strided rows, so stacked gate and up or a layer's per-layer inputs are read in place), and `ptx::QUANT_Q8P` now one value per thread, a Q8P block being two warps; `EMBED_Q4` embeds a token per grid row.
- `ptx::GEMM_Q4`, the prefill matrix product on tensor cores: integer `mma.sync` (m16n8k32) on the Q4 weights and Q8P activations, 128 tokens × 64 rows per block, operands staged in shared memory by `cp.async`. Q8P (`quant::q8p`, `ptx::QUANT_Q8P`) is the prefill activation layout: one scale per 64 values, so a Q4 group's two `mma` chain in integers, with a second word that folds the zero point and a magic-number bias into one `fma`. `ptx::MMA_PEAK` measures the integer tensor-core ceiling; the `prefill` bench reports every E4B projection over 512 tokens against it.
- `tachyon::engine`: the chat API. `Engine::open` loads a model directory on GPU 0; `Engine::chat` takes a `Request` (messages, thinking, sampling, most tokens) and returns a `TokenStream`, whose `next_text` hands out the answer's text as it is generated, allocating nothing; dropping the stream cancels the answer. A prompt longer than the context is `Error::TooLong`. `tachyon run` is built on it.
- `scripts/llamacpp.sh`: the step-6 comparison, llama.cpp with CUDA at a pinned commit decoding Gemma 4 E4B in Q4_0, measured by `llama-bench`.
- `scripts/reference.py`, which writes Hugging Face's bfloat16 answers for the engine's top-1 agreement test (≥ 86%), and `scripts/agreement.py`, which measures what each way of rounding the weights allows.
- `Decoder::start`, `next_token` and `stop`: decoding with the next step always queued behind the running one (two recordings of the step trade the token words), so the GPU never waits for the CPU. `Decoder::timeline` and `Decoder::alone` profile a step kernel by kernel and each kind of kernel alone; the `generate` benchmark reports both and gates decode at ≥ 80% of the roofline: 107–109 tok/s on the RTX 3060 Laptop (81–83%), against 61–77 tok/s for Ollama (llama.cpp) on the same machine.
- `ptx::GEMV_Q4_NARROW`, the decode GEMV for rows of 256 weights: 8 lanes per row. `ptx::SPIN`, a kernel that holds the GPU, for profiling.
- `tachyon::model::Decoder`: Gemma 4 on the GPU. One decode step (embedding, per-layer inputs, 42 layers of sliding or global attention with shared caches, LM head, sampler) is recorded once as a CUDA Graph; the token goes in and comes out through one pinned host word, so the CPU only waits. Tested against a CPU reference that matches Hugging Face transformers to 1e-5, on a generated tiny Gemma 4. `tachyon run <model> <prompt>` answers a prompt greedily and reports the speed.
- `tachyon::model`: Gemma 4's decoder configuration and `convert`, which turns a Hugging Face checkpoint into a model directory: Q4 weights for VRAM with query/key/value and gate/up fused, the per-layer embedding table for pinned host memory, the stored tokenizer. `tachyon convert <checkpoint> <model>` runs it. `tachyon::quant::Safetensors` reads checkpoints a slice of rows at a time, so a checkpoint larger than memory converts.
- `tachyon::token`: the tokenizer. `Tokenizer::from_json` reads a Hugging Face `tokenizer.json` (BPE with byte fallback, as Gemma uses), `to_bytes`/`from_bytes` store and load it ready to use; `encode` matches `tokenizers` exactly on 10,000 strings in 34 languages, emoji and code, and cuts the text where no merge can cross. `Detokenizer` emits whole characters as tokens arrive. `Chat` is Gemma 4's chat template coded by hand, with the system turn and thinking switch; turn markers enter only by ID, so text cannot forge them.
- `tachyon::json`: a JSON reader for model files.
- `token` benchmark, with the step-5 exit gate; `scripts/fixture.py`, which makes the tokenizer fixtures.
- `tachyon::quant`: Q4 weights (groups of 64, f16 scale, zero point 8, packed for `dp4a`) and Q8 activations (blocks of 32 with their sums), and exact f16 conversion.
- `tachyon::ptx`: kernels generated as PTX text for `sm_80`+: `quant_q8`, and `gemv_q4`, the decode matrix-vector product, Q4 × Q8 with `dp4a`, one warp per row and every load of a short row in flight at once.
- `tachyon::ptx`: the rest of the decode kernels. `norm_q8`, the residual add with RMS normalization and the next input's Q8; `geglu_q8`, the GELU-gated activation into Q8; `embed_q4`, a Q4 embedding row from VRAM or pinned host memory; `attend_256` and `attend_512`, decode attention with query and key norms, RoPE (including Gemma 4's proportional RoPE through `ptx::rope`), an `f16` key-value cache as a sliding window or global, shared caches, and positions split across blocks; `sample`, greedy or exact sampling with temperature, top-k, top-p, min-p, repetition penalty, an allowed-token mask and logit soft-capping, set through `ptx::Sampling` in device memory.
- `decode` benchmark: every non-GEMV kernel per launch, and one E4B token's worth against a decode step at the VRAM ceiling.
- `gemv` benchmark: every Gemma 4 E4B projection, including the per-layer input projections, against the measured VRAM read bandwidth, with the step-3 exit gate: one token's projections, weighted by bytes, at ≥ 90%.
- `tachyon::wpk`: the `.wpk` weight file (4 KiB-aligned tensors, checked header and table, CRC32C per tensor) with `Writer`, `Wpk::open`, `Wpk::verify`.
- `wpk::Loader`: `io_uring` reads with `O_DIRECT` straight into pinned memory; disk → VRAM through staging slots overlapped with uploads, disk → host-RAM tier, and host tier → VRAM. `Reads::Auto` reads through the page cache when it already holds the file (a model a previous process loaded) and with `O_DIRECT` otherwise.
- `load` benchmark: every load path on a file sized to the machine, with the step-2 exit gate.
- `tachyon::cuda`: the CUDA Driver API loaded at run time from `libcuda.so.1` (or `/usr/lib/wsl/lib`, or `$TACHYON_LIBCUDA`), with every function fetched at the CUDA 12.0 ABI so newer drivers keep working.
- Owning, non-`Send` wrappers: `Context` (primary context), `DevBuf`, `HostBuf` (pinned, mappable), `Stream`, `Event`, `Module` (PTX with the JIT error log), `Graph` (stream capture and replay).
- `tachyon gpu [--json]`: the GPUs the driver sees, with compute capability, memory, datasheet bandwidth and PCIe link.
- `machine` benchmark: VRAM read bandwidth, PCIe in both directions, launch and graph-replay cost, with the step-1 exit gate.
- Bench harness with `perf` counters, JSON results and a 3% regression check against per-machine baselines.
- `ci.sh`: format, clippy pedantic, docs, complexity, line budgets, tests, PTX checks.
